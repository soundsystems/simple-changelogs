# Skill-Repository Backfills

Start the initial backfill when the user confirms onboarding with its displayed
default, unless they defer or decline in the final question. Later historical
audits still require an explicit current decision or recorded policy authority.
Silence without a confirmed receipt authorizes nothing.

Use tags, commits, package manifests, archived skill directories, published
packages, hosted releases, README install docs, and eval history as evidence.
State uncertainty rather than inventing versions, dates, shipped behavior, or
compatibility.

The initial backfill during adoption must cover the complete accessible
history, from the oldest trustworthy evidence through the setup boundary.
Review every intervening range and account for every historical change across
the public and developer histories. Related commits may become one durable
outcome, and abandoned, reverted, noisy, private, or unsupported candidates may
be omitted, but record the reason for each omission instead of silently
sampling recent commits or highlights.

Safe drift repair can copy an unambiguous released value into an established
mirror, or restore a missing generated packaged note or empty `Unreleased`
heading. Deleting, materially rewording, collapsing, moving release boundaries,
or changing the audience of released entries requires explicit
meaning-changing authority.

When an approved audit begins, record `partial`; set `completed` only after the
requested range and all established mirrors are verified. For an initial
backfill, the requested range is always the complete accessible history; a
shallow clone, missing release records, or another evidence gap keeps the audit
`partial` or `failed` until resolved. Use `deferred` or `declined` only for the
user's actual disposition.
